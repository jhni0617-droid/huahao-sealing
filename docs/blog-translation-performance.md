# 博客多语言翻译 · 性能诊断与优化报告

> 日期：2026-09-10 · 对象：`scripts/translate-blog.ts` 与博客数据的运行时加载

基线：94 篇文章 × 5 语种 = 470 个翻译单元，全量翻译用时 55.6 分钟，
输入 2,735,938 / 输出 1,410,653 tokens（gpt-4o-mini）。

---

## 一、诊断：瓶颈在哪

先把"感觉慢"变成"哪里慢"，两处独立瓶颈：

### 瓶颈 A：翻译脚本 —— system prompt 被反复重发

关键公式：

```
总请求数 = Σ(每单元块数) + 单元数 × 每单元固定请求数
输入 token ≈ 总请求数 × system prompt 长度 + 原文 token 总量
```

实测反推：

| 项 | 数值 |
|---|---|
| 每单元正文平均长度 | 6,338 字符（中位 6,196 / P90 9,874 / 最大 25,380） |
| 原分块阈值 | 3,500 字符 → **1,086 块**（2.31 块/单元） |
| 每单元固定请求 | 2 次（标题、摘要各一次） |
| **总请求数** | **2,026 次** |
| 反推出的 system prompt 长度 | 约 627 tokens |
| 纯 system 重复量 | 2,026 × 627 ≈ **127 万 tokens（占输入 47%）** |
| 另：落盘方式 | 每完成 1 项全量重写 6 MB JSON → 470 次 ≈ **2.9 GB 磁盘写入** |

**结论：请求数被分块策略放大了 4.3 倍，而近一半的输入 token 花在重复的 system prompt 上。**

### 瓶颈 B：站点运行时 —— 8.2 MB 的 server chunk

`lib/blog-data.ts` 里 `import blogTranslations from "../content/blog-translations.json"`，
使 6 MB 译文被整体打包：

| 项 | 实测 |
|---|---|
| 最大 server chunk | `.next/server/chunks/_0vgbsam._.js` = **8,253 KB** |
| 构成 | 译文正文 6.5 MB + 中英原文 1.6 MB |
| 模块加载耗时 | 172 ms（读盘 36 + 解析 12 + 聚合 124） |
| 堆内存占用 | 约 50 MB |
| 单篇博客页真正需要的数据 | **3 KB**（浪费比约 1,000 倍） |
| sitemap / 列表页真正需要的数据 | 52 KB（只需标题摘要） |

同时确认：**客户端 bundle 是干净的** —— 译文不进客户端包（列表页走
"服务端解析当前语言 → 传 props"通道，RSC 载荷 36 KB/语种）。

## 二、已实施：翻译脚本侧优化

改动集中在 `scripts/translate-blog.ts`，四项：

| # | 改动 | 说明 |
|---|---|---|
| 1 | 分块阈值 3,500 → 8,000 字符 | 块数 1,086 → 540，请求数减半 |
| 2 | 显式 `max_tokens: 16384` | 放宽阈值的前提，防止长块被服务端默认上限截断 |
| 3 | 标题 + 摘要合并为一次请求 | 一次返回 `{"title","excerpt"}` JSON，失败自动回退分开翻 |
| 4 | 落盘节流（每 10 项或 20 秒） | 替代"每项全量重写"，写入量 −90% |
| 5 | 默认并发 4 → 8 | 可用 `--concurrency=` 覆盖 |

新增可调参数：`--chunk=N`（分块阈值）、`--maxTokens=N`（输出上限）。

### 效果

| 指标 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| API 请求次数 | 2,026 | 1,010 | **−50%** |
| 输入 token | 2.74 M | 2.10 M | **−23%** |
| 磁盘写入 | 2.9 GB | 0.3 GB | **−90%** |
| 全量翻译耗时 | 55.6 分 | 预计 ≈18 分 | **−68%** |

### 质量验证（同一篇 `carbon-graphite-seal-ring-basics` → 越南语实测重翻）

| 项 | 旧译文 | 新译文 |
|---|---|---|
| H2 / H3 / 列表项 | 6 / 7 / 5 | 6 / 7 / 5（**结构指纹完全一致**） |
| 正文字符数 | 6,079 | 5,952（长度比 0.98） |
| 术语命中（than chì / đệm kín / ngâm tẩm） | 25 / 5 / 11 | 25 / 6 / 12 |
| 结尾完整性 | 完整 | 完整（无截断） |

该篇实测单任务输入 token：**2,954**（旧逻辑同篇推算约 4,243）。

全站校验：`npm run translate:blog:verify` → **470/470 全绿，零告警**。

> 注意：已有译文质量已合格，**无需重跑**。本次优化在下次翻译
> （新增文章 / 新增语种）时自动生效。

## 三、待决策：站点侧的 8.2 MB server chunk

### 方案

把译文从"单文件静态 import"改为"按篇拆分 + 按需加载"：

```
content/blog-translations/
  _index.json                        # 94 篇 × 5 语种的标题+摘要，424 KB
  carbon-graphite-seal-ring-basics.json   # 单篇 5 语种（平均 65 KB，最大 179 KB）
  ... 共 94 个文件
```

- 列表页 / sitemap → 读 `_index.json`（424 KB）
- 单篇博客页 → 只加载自己那一篇（65 KB）
- 翻译脚本继续写单文件，落盘后自动派生拆分产物（或提供 `npm run split:blog`）

预计 server chunk：8,253 KB → 约 2,050 KB（**−75%**）。

### 但先看这笔账值不值

博客文章页走 **ISR**（`generateStaticParams` 返回 `[]` + `revalidate = 86400`）：

- 数据加载只发生在**冷渲染**时（每篇 × 每语种 × 每 24 小时一次）
- 之后命中缓存直接返回，**不加载数据**
- 所以收益是"恰好第一个访问者快约 130 ms"，普通用户无感

**判断标准：**

| 情况 | 建议 |
|---|---|
| 当前规模（94 篇、ISR 缓存） | 收益有限，可缓做 |
| 文章量涨到数百篇 | 建议做 |
| 部署到 Vercel 且 function 体积吃紧 | 建议做 |
| 改为构建期全量预渲染博客页 | 收益最大，但受部署文件数限制 |

**不做的代价**：`.next` 多 6 MB；冷渲染多约 130 ms。
**做的代价**：新增 94 个文件 + 动态 import 层，调试路径变长。

## 四、复现命令

```bash

# 校验
npm run translate:blog:verify                     # 覆盖率 + 结构一致性，退出码可挂 CI

# 诊断 server bundle
find .next/server -name "*.js" -size +200k -exec ls -la {} \; | sort -k5 -rn | head
```
